# DuckDB dashboard query research

Research checked against DuckDB's official 1.5 documentation on 2026-10-20. The running collector uses 1.5.6. Recommendations below combine that guidance with the supplied measurements; no new benchmarks were run.

The next useful measurement is operator profiling on a fixed dataset of roughly 3 million rows, followed by a short mixed ingestion/read test of any promising change. Earlier profiling at 1.4 million rows already produced an adopted summary rewrite, reducing median execution from 196.83 to 141.39 ms. The latest event-page maxima, 311 ms executing and 2,909 ms waiting across 317 reads, make the serial reader queue a separate optimization target. Execution here includes the snapshot transaction, SQL and Rust decoding/response construction; it is not a SQL-operator timing. Those maxima need not describe the same request.

DuckDB's documented guidance:

- `EXPLAIN ANALYZE` executes the query and reports operator timings and cardinalities. JSON profiling can capture scans, aggregation, windowing, and sorting. Record `OPERATOR_ROWS_SCANNED`, `OPERATOR_CARDINALITY`, `OPERATOR_TIMING`, `LATENCY`, `SYSTEM_PEAK_BUFFER_MEMORY`, and `SYSTEM_PEAK_TEMP_DIR_SIZE`. Keep the application's queue timer alongside them: DuckDB's `BLOCKED_THREAD_TIME` measures waiting for an engine thread, not waiting in the application's reader queue. [Profiling](https://duckdb.org/docs/current/dev/profiling), [metrics](https://duckdb.org/docs/current/dev/metrics).
- Grouping, sorting, and windowing are blocking, memory-intensive operations. Check whether project filters reach the scans and where rows accumulate. Prepared statements save parsing and planning; DuckDB describes their benefit mainly for repeated queries below 100 ms. They do not cache aggregate results. [Workload tuning](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads).
- Automatic zonemaps skip row groups whose value ranges cannot satisfy a filter. Physical ordering by frequently filtered columns improves this pruning. For this collector, compare scanned rows against project selectivity and the ordered `ingest_id` cursor. Ordering cannot eliminate the work needed to aggregate every relevant row in an all-history project query. [Indexing](https://duckdb.org/docs/current/guides/performance/indexing).
- ART indexes mainly help highly selective equality or `IN` lookups. Only single-column, expression-free indexes qualify for index scans; the default threshold is `max(2048, 0.001 × table_rows)`, about 3,200 matches at 3.2 million rows. They do not directly accelerate grouping or sorting, and add write and memory costs. This supports retaining the prior index rollback unless a measured selective scan justifies another attempt. [Indexing](https://duckdb.org/docs/current/guides/performance/indexing).
- DuckDB permits concurrent work within one process; reusing connections avoids connection overhead. More threads can slow a workload, and the performance guide suggests 1–4 GB of memory per thread. The prior mixed-load result supporting `threads=1` outweighs a generic recommendation to use all six CPUs. [Concurrency](https://duckdb.org/docs/current/connect/concurrency), [connection and thread guidance](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads), [memory guidance](https://duckdb.org/docs/current/guides/performance/my_workload_is_slow).

Application proposals to evaluate after profiling:

1. Compute the shared per-view reconstruction once for a dashboard refresh and derive both summary and video results from it. Coalesce simultaneous identical refreshes. A short, explicit freshness window could reduce repeated reads further if the product permits stale results.
2. If reconstruction dominates, maintain a compact per-view state table or periodically rebuild a snapshot. Preserve earliest-start attribution, latest cumulative playtime, null behavior, late events, and tie handling. Keep exact distinct-viewer counts correct across videos; summing per-video distinct counts is insufficient. Measure the extra writer work before adopting this.
3. If waiting dominates after reducing repeated work, trial bounded scheduling or a second reader connection for event pages. Measure page latency, ingestion failures, memory, and checkpoint stalls together. More reader concurrency may increase contention.

These are application-managed reuse strategies. A normal DuckDB view reruns its query whenever referenced; it does not materialize or automatically maintain the result. [CREATE VIEW](https://duckdb.org/docs/current/sql/statements/create_view).

## Local evidence and correctness constraints

The measurements come from the 2026-10-20 local benchmark reports in `/Users/ftatilon/Dev/benchmarks/chunkify-analytics/2026-10-20`: `query-optimization-summary.md`, `lookup-optimization-summary.md`, `thread-tuning-summary.md`, and `isolated-soak5000-ten-minute.json`. The temporary soak database was removed after verification. A new fixed-dataset probe must remain bounded and clean up its generated database.

Current implementation references: `src/store.rs` reconstructs per-view state separately for summary and videos; `src/reader.rs` serializes reads; `src/storage.rs` bounds event rows before the OTLP join. Summary date and context filters select view starts. Pushing those filters onto all raw events could omit later cumulative playtime and change results. Any reused state or cached response must retain project isolation, filter identity and pagination snapshot semantics. Retention, deletion and restart behavior also need defined handling before persistent derived state is adopted.
